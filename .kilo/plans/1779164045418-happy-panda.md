# План рефакторинга и оптимизации ASK-Apache-Airflow

## Цели

- Устранить «висящих воркеров» и накопление зависших процессов.
- Снизить нагрузку на исходную БД (`tim_db_pluginsdb`) и метаданные Airflow.
- Привести конфигурацию к согласованному состоянию (Celery + Postgres) без правок `config/airflow.cfg` (через env в `docker-compose.yaml`).
- Сохранить **точную семантику** ETL: имена таблиц, колонок, схема `datalake.*`, расписания и итоговые данные не меняются. Все изменения — внутренние (производительность, надёжность, корректность).

## Принципы

1. Никаких изменений схемы выходных таблиц и расписаний DAG.
2. `if_exists="replace"` остаётся `replace` (на этом этапе не переходим на TRUNCATE/UPSERT).
3. Секреты (fernet_key/jwt_secret/secret_key) **не трогаем** — это потребует ротации и расшифровки существующих connections.
4. Все правки конфигурации — только в `docker-compose.yaml` через `AIRFLOW__*` env. `config/airflow.cfg` не редактируется.
5. Каждый этап коммитим отдельно, чтобы можно было откатиться.

## Этап 2. Защита от зависаний

### 2.1. `execution_timeout` для всех @task
Добавить дефолтные `default_args` или явные `execution_timeout` в каждый `@task` всех 5 DAG'ов:
- extract-таски: `timedelta(minutes=15)`
- transform-таски: `timedelta(minutes=20)` (для `plugin_engagement` — 30 мин временно, до этапа 3)
- load-таски: `timedelta(minutes=20)`

Реализация — централизованно через `default_args = {"execution_timeout": ..., "retries": 1, "retry_delay": timedelta(minutes=5)}` в каждом `@dag(...)` (или единый helper в `dags/common/config.py`).

### 2.2. Ограничения параллелизма на уровне DAG
В каждом DAG (декоратор `@dag` или `with DAG`):
- `max_active_runs=1` — запретить наложение запусков одного DAG (главная защита от «накопления»).
- `max_active_tasks=4` — разумный лимит на одновременные таски внутри DAG.
- `catchup=False` (уже стоит).

Это решает основную проблему: если запуск занимает >расписания, новые не стартуют, пока не завершится текущий.

### 2.3. Heartbeat / killed-task-cleanup
- Сейчас `task_instance_heartbeat_timeout = 300` оставляет «зомби»-процессы.
- Через env в docker-compose поднять/настроить:
  - `AIRFLOW__SCHEDULER__TASK_INSTANCE_HEARTBEAT_TIMEOUT=600` (даём задаче больше времени отвечать на heartbeat).
  - `AIRFLOW__CORE__KILLED_TASK_CLEANUP_TIME=120` (секунд на корректное завершение перед SIGKILL).
- Дополнительно установить `statement_timeout` на сессию psycopg2 (см. этап 3) — если запрос завис, сама БД его прервёт.

## Этап 3. Оптимизация производительности ETL

### 3.1. Инкрементальные запросы в extract (вместо `SELECT *`)
Файл: `dags/etl_pipelines/extract/pluginsdb.py`.

| Функция | Сейчас | Стало |
|---|---|---|
| `extract_logs` | `SELECT * FROM plugins.log` | `SELECT ... FROM plugins.log WHERE created_at >= NOW() - INTERVAL '7 days'` (или окно через Variable, как в `extract_added_incremental`) |
| `extract_monitoring` | `SELECT * FROM plugins.monitoring` | `WHERE event_time >= NOW() - INTERVAL 'N days'` |
| `extract_project_sync` | `SELECT * FROM projects.project_sync` | `WHERE updated_at >= NOW() - INTERVAL 'N days'` |
| `extract_ad_users` | `SELECT * FROM users.ad_user` | оставить как есть (справочник, малый размер) — но добавить `LIMIT` как защиту от внезапного роста |

Размер окна (N) согласовать через Airflow Variables: `LOGS_EXTRACT_WINDOW_DAYS`, `MONITORING_EXTRACT_WINDOW_DAYS`, `PROJECT_SYNC_EXTRACT_WINDOW_DAYS` — дефолтно 7/14/30 дней.

**Важно:** для `if_exists="replace"` логика DAG ожидает «полный пересчёт». Уменьшение окна меняет содержимое выходной таблицы. Поэтому:
- Для `logs_etl_dag` (replace) — окно должно быть достаточным, чтобы сохранить аналитический горизонт. Согласовать с владельцем (по умолчанию: 90 дней). Альтернатива — мигрировать на `incremental` режим (вне scope этого этапа).
- Для `projectsync_etl_dag` (incremental) — фильтр безопасен.
- Для `plugin_engagement_etl_dag` — см. п. 3.3 (там целевая оптимизация другая).

> **Решение по сохранению семантики**: на этом этапе **сохраняем поведение** для replace-таблиц — добавляем фильтры только там, где это не меняет итоговые данные (`projectsync` уже incremental, `added_elements` уже incremental). Для `extract_logs`/`extract_monitoring` — выносим окно в Variable с дефолтом «достаточно большим» (например, 365 дней), но добавляем явный `LIMIT N` (1_000_000) как safety net. Если будет подтверждено, что данные старше 90 дней не используются — окно сократить отдельным change-request.

### 3.2. Statement timeout на стороне БД
В `extract` функциях перед `pd.read_sql` выставлять:
```sql
SET statement_timeout = '900s';   -- 15 минут
SET idle_in_transaction_session_timeout = '60s';
```
Это финальная защита: даже если воркер не сработает по `execution_timeout`, БД сама прервёт зависший запрос.

Реализация: вспомогательная функция `_apply_session_timeouts(conn)` в `dags/common/utils.py`, вызывается из всех extract-функций.

### 3.3. O(N²) в `plugin_engagement.py`
- Файл: `dags/etl_pipelines/transform/plugin_engagement.py:186-220`.
- Цикл `for current_day in all_dates: df_until_day = df_designers[df_designers['day'] <= current_day]` переписать через **векторизованные операции pandas**:
  - вычислить ежедневные агрегаты `groupby('day').agg(...)`,
  - применить `cumsum()` / `expanding()` для кумулятивных метрик,
  - либо `pivot` + `cumsum` по оси day.
- Сложность: O(N²) → O(N log N).
- **Обязательно** написать тест на эквивалентность результатов: на синтетических входных данных результат старой и новой реализаций должен совпадать (`pd.testing.assert_frame_equal` с сортировкой по ключам).

### 3.4. `iterrows()` + `df.loc` в `added_elements.py`
- Файл: `dags/etl_pipelines/transform/added_elements.py:401-406`.
- Заменить:
  ```python
  for idx, row in df_first.iterrows():
      interval = row.get('corrected_interval')
      if pd.notna(interval) and interval <= SESSION_GAP_SECONDS:
          df.loc[idx, 'time_since_prev_sec'] = interval
  ```
  на:
  ```python
  mask = df_first['corrected_interval'].notna() & (df_first['corrected_interval'] <= SESSION_GAP_SECONDS)
  df.loc[df_first.index[mask], 'time_since_prev_sec'] = df_first.loc[mask, 'corrected_interval']
  ```

### 3.5. Логи pandas
В extract/transform добавить INFO-логирование числа строк после каждого read_sql и ключевых трансформаций (`logging.info("extract_logs: %d rows", len(df))`) — чтобы было видно, какая задача физически тяжёлая.

## Этап 6. Структурные улучшения (low-risk)

### 6.1. Общий helper `dags/common/db.py` (новый файл)
Чтобы устранить дубликацию кода в extract:
```python
# dags/common/db.py
from contextlib import contextmanager
from airflow.providers.postgres.hooks.postgres import PostgresHook

@contextmanager
def pg_connection(conn_id: str, statement_timeout: str = "900s"):
    hook = PostgresHook(postgres_conn_id=conn_id)
    conn = hook.get_conn()
    try:
        with conn.cursor() as cur:
            cur.execute(f"SET statement_timeout = '{statement_timeout}'")
        yield conn
    finally:
        conn.close()
```
Использовать во всех extract-функциях `pluginsdb.py` и в load `datalake.py`.
